# explain-plainly

## How to explain
- **Big picture first.** Three to five bullets: what it is, what it does, why it
  matters. Details after, only if needed.
- **Plain words.** Define each term the first time in one short sentence. No
  unexplained acronyms.
- **Numbers mean something.** Say what a figure measures, its range, and whether
  the value is good.
- **Short.** If the user says it's too much, halve it and keep only what they
  need to act.
- Base every claim on the actual files, output or results. Don't guess.

## Talking points
When the user has to present or report the work, answer in their frame. A good
default:
1. What exists now.
2. What comes next.
3. What the finished thing will be.
4. What is new or valuable about it.
Add the likely questions with one-line answers.

## Getting up to speed
Give an ordered path that fits the time the user has: run it, then read the
entry point, the core module and one test. Pair each step with the doc or
source that explains the idea behind it.
